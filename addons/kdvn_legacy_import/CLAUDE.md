# kdvn_legacy_import (Odoo 19)
Re-runnable import of Odoo 12 data (dev test data now, go-live migration later). Design decided 6 Nov 2026: SQL read, ORM write.
- Source: database `legacy12` on the Odoo 19 Postgres (param `kdvn_legacy.db`), made by `tools/legacy12_snapshot.sh` (pg_dump of att18mar from `kdvn.odoo12.db.dev`, ~75 s, 1.5 GB). The two Postgres containers are on different docker networks, hence the copy. Read-only session; same server and login as Odoo.
- Every record gets external id `legacy12.<odoo12 table>_<id>`. Rerun = update; an untagged record with the same natural key (employee code or linked user, user login, department code, location name, type code) is adopted and tagged; else created. Odoo 12 users 1 and 2 map to `base.user_root` / `base.user_admin` and are never rewritten.
- A bad row is rolled back in a savepoint, counted, and listed in the log; the run goes on.
- Scope: `employee_codes` (empty = all) + `working_only`; managers (parent, admin manager, department managers) of the chosen staff are always added so chains stay whole.
- Odoo 12 values are copied as they are (parent, admin manager, sections), not recomputed from history; history is then loaded with `kdvn_defer_org_refresh` and the manager-user chains are computed once at the end.
- Groups: legacy group -> Odoo 19 group with the same xml id, module `kderp_x` renamed `kdvn_x`; `base.*` never copied. Groups with no counterpart show in the log as "legacy group not mapped": the module that needs them maps them when it is ported.
- Not imported yet: employee photos, leave balances, attendance and requests (later steps of kdvn_hr_attendance; add steps by extending `_import_steps` in your own module).
- `password` option (dev only) sets one password on all imported users. Never use it on a real database.
- Wizard: Settings > Technical > Import from Odoo 12 (system admins). From code / shell: `env['kdvn.legacy.import'].run(employee_codes=[...], working_only=True, password='...', dry_run=True)`.
- Tests use a small fake snapshot (no `legacy12` needed): `-u kdvn_legacy_import --test-tags /kdvn_legacy_import` (12 tests).

## Attendance data (7 Nov 2026)
`models/legacy_import_attendance.py` adds steps when kdvn_hr_attendance is installed: company policy, calendars, public holidays, face machines, state/status code mapping, rules (+ members), attendance days of the window (+ status marks), raw checks, requests, OT holiday plans. Window = wizard/`run(date_from=, date_to=)`; staff = the selected employees. Stored Odoo 12 values are copied as they are (`do_not_run_at_status`): nothing is recomputed.
Not imported yet: leave covers, leaves, allocations (stage B), refuse log, summaries (SQL views, follow the data), photos.
Trial (scratch DB, 8 staff + managers = 34 staff, 21 Oct - 20 Nov 2026): 408 attendance days, 271 raw checks, 259 rules in ~35 s. Parity check (recompute in Odoo 19 vs Odoo 12 stored): 381 of 408 identical, OT hours 100 % identical; the 27 differences are Saturday AH days (need stage B).

## E-approval data (8 Nov 2026)
`models/legacy_import_e_approval.py` (steps ea_requests, ea_reviews, ea_chatter, ea_attachments, ea_check, before `prune`): requests of the procedures in `EA_MODELS` (entertainment, peak time, staff transfer; safety tool has child lines: not yet), their `tier.review` rows (Odoo 12 status, reviewers, can_review, todo_by copied; in-flight requests keep their pending step and the right reviewer can act), chatter with tracking values, followers (default subtypes), attachments (files from `temp/legacy_filestore`, parameter `kdvn_legacy.filestore`, extracted by `tools/legacy_nightly.sh` from the HN `<db>-daily.filestore.tgz`; res_id 0 files are found through the request's attachment list).
- `state` is written with SQL, never through the ORM (the tier validation engine would open or validate reviews); other fields go through the ORM with `skip_validation_check`. `validation_status` is recomputed once after the reviews. Nothing is notified: no tracking, mail, activity, n8n, Talk.
- Tier definitions are NOT imported: the procedure modules ship them (`data/*_tier_definitions.xml`, equal to HN production). Mapping: same xml id with kderp_ -> kdvn_, else model + name. The target database must have them (`-u kdvn_entertainment_procedures,kdvn_hr_procedures`), else every review is listed as a problem.
- Window: requests created/changed since date_from or not decided yet; full run = all. Messages, tracking values and files are imported once.
- Prune: reviews, messages, files and requests whose Odoo 12 row is gone (same safety limit). `ea_check` compares state + review statuses of every loaded request with Odoo 12; a difference is a problem line.
- Trial on the 8 Nov HN snapshot (copy of odoo19_dev): 40 requests, 86 reviews, 327 messages, 180 tracking values, 24 files (checksums equal), 39 followers; second run changes nothing; no mail/activity created. Odoo 12 history that violates today's rules is copied (context `kdvn_legacy_import` skips the amount > 0 check).
