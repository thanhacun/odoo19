## Deviations from Odoo 12 (each one only where Odoo 12 crashed, returned a wrong "None", or Odoo 19 changed the API)
- D1 `hr.holidays.public.is_public_holiday` returns 0 (not None) when the year has no holiday lines. Odoo 12: None, so `== 0` checks treated every day as a holiday. Production always has the year entered.
- D2 `is_no_sat_working` returns False when no calendar rule exists (Odoo 12: ValueError from min of nothing).
- D3 `hr.mixin._get_early_offset` looks for `early_in` requests only when `hr.attendance.request` exists (stage C).
- D4 `hr.attendance.rule._search_is_active` understands the operator forms Odoo 19 produces (`in`, `not in`, `!=`).
- Groups: Odoo 12 also renamed core groups ("Manual" -> removed in 19, "HR Admin" label) and made `director` imply the manual group; not copied. Record rules on `hr.attendance` come with stage A2 (they use `view_user_ids`).

## Business rule: ONE leave type per day (payroll)
The salary system (third-party app, reads our results) does not accept a day that carries two different leave types. Never "fix" a conflict by letting two types coexist on one day (e.g. AH + another type, or two half-day covers of different types); keep the Odoo 12 checks that refuse it and port them literally. When a parity or import run shows a day with two types, treat it as a data/rule problem to explain, not something to allow. Noted 7 Nov 2026 (Thanh).

## Period lock (9 Nov 2026, 19.0.0.14.1; branch feature/period_lock; Thanh's decisions: 3 months, HR Admin unlocks, no list of not-done days, no archiving)
Payroll values are the source of truth: an attendance period (21st..20th) that ended more than `res.company.lock_months` months ago (default 3, Settings > Attendance, 0 = no lock) is LOCKED, whatever its state. Code: `models/period_lock.py` (helpers on `hr.mixin`, the unlock model, decorator `skip_locked`).
- Cutoff = first day of the attendance period that holds (today - lock_months): days before it are locked (`hr.mixin._period_lock_cutoff`).
- hr.attendance: `write()` of the fields in `PERIOD_LOCK_FIELDS` (hr_attendance_main.py) raises UserError on a locked day, `create()` / `unlink()` too; a manual assignment of a COMPUTED field (e.g. `at.request_description = ...`) is dropped for the locked day silently; `_write_multi` (the flush of stored computes) keeps the stored values of locked days and invalidates the cache; `@skip_locked` on `_compute_at_status`, `_compute_related_states`, `_compute_ot_request`, `_compute_ot_allow`. Fields `active`, view users, department/managers/area stay editable.
- Requests (`hr.attendance.request`), leave covers and leaves: create / state change / date change / delete on a locked day raise UserError (a leave spanning locked and open days is refused, the message lists the locked dates). Raw-data sync skips locked days (log line `period lock: raw sync skips`).
- Unlock: `hr.attendance.period.unlock` (menu Attendance > Configuration > Period unlocks, group `hr_attendance.group_hr_attendance_user` = "HR Admin" of Odoo 12): employee (empty = all), dates, mandatory reason, expires_at (default +1 day, the days lock again by themselves), a note on every unlocked day. Not editable, not deletable (audit); "Lock again" ends it. `period_locked` (boolean, searchable) + form ribbon + filter "Period locked".
- Bypass: context `kdvn_period_lock_off` (the legacy importer's `run()` sets it; the SQL bulk loader does not use the ORM). sudo() does NOT bypass.
- Places a write can still get around the guard: raw SQL; `_write` of other models that store copies (hr.leave.cover dates, summaries); an unlock window; `kdvn_period_lock_off`; stored fields not in `PERIOD_LOCK_FIELDS` (add them there); writes made by Odoo through `hr.attendance.write` on `message_*` fields are allowed on purpose.
- To mirror in Odoo 12 production (Thanh's rule, see HANDOFF): same design, Python 3.6, baseline before/after.
